# 反哺规则（派活反馈）

一次任务结束时，只有当这次来回确实由"只有用户能补的信息缺口"造成，才在交付末尾
追加一句轻量反馈，训练用户内化更好的派活方式。默认宁可沉默。

## 一、先过三道闸——任一为"是"就闭嘴（锅在我，不许发）

- 可读吗：答案在代码 / 配置 / 文件里，我查一下就有，却靠反问拿到？→ 我偷懒，闭嘴。
- 可默认吗：候选唯一，或有明显约定俗成 / 上下文默认，我却把本可自己定的抛回用户？→ 闭嘴。
- 是我先猜错吗：来回是我没澄清就动手、方向猜歪返工造成的？→ 我的失误，闭嘴。

三闸全过——答案不在任何可查处、候选真有多个且无默认、歧义在派活那一刻就客观存在——
才算"只有用户能补"，即可发（有一次真实来回即可，不必等它反复出现）。凡我能靠读代码 /
查文件 / 合理默认自行消除的来回，一律不触发。宁可漏报，绝不错怪。

## 二、怎么说——邀请，不是纠正

句式把成本落在我的处理开销上，不是用户的表达错误。禁"你没说 / 你缺了 / 下次要说"这类
诊断句，禁"更顺 / 更好"这类隐含"你上次差一步"的比较级；用"补一句就能省掉"的增量邀请：

> 🔄 派活提示：这次我为了定「<我当时不得不猜的那类信息>」多<绕了一圈 / 问了你一轮>。
> 这点查不到、只有你知道——下次随手带一句「<可照抄的那句>」我就能一次到位 (｡•̀ᴗ-)✧

- 一次任务最多一句；这一句是"帮我省一步"，不是"你刚才错了"。
- 若同一类缺口本次会话内已第二次要我猜，这唯一的一句可改为点"类别"
  （"这已是第二次要我猜目标端了"），而非再点具体这一次——不加条数，只提层级。

## 三、范本里能放什么——按"来源时刻"卡，不按类型

核心：用户握意图，AI 挖事实；范本只能落在用户那一侧。判据不是"这词是不是哈希 / 变量名"，
而是——用户按回车那一刻，这东西在不在他手里（脑子里或他贴的文本里）？

- 在 → 可用：他自己的说法、他选的分支 / 环境（dev/test）、他贴来的报错 / 文件名、
  我反问过而他当场答出的信息（正因答得出，才可要求他下次一次说全）。
- 不在 → 禁入，删成意图：我读代码 / 查库 / 跑工具才拿到的哈希、变量名 / 函数名、路径、
  行号、我定位出的分支归属；他贴来的报错可用，但我查出来的同名文件不可用（来源不同待遇不同）。
- 模糊说法：保留他的原话，我只把"缺的那类信息"点成占位（"带上在哪个分支解"），
  绝不替他填具体值。精确到"该补哪一类"为止。

发出前唯一自检：范本里每个具体标识，用户当时说得出、或贴得出吗？说不出——删成意图；
删空了就不发。

## 四、边界

不写任何记忆、不跨任务积累、不主动提醒；靠当场这一句持续训练用户自己内化。
