# 反哺规则（派活反馈）

这是一条极稀有的规则。绝大多数任务都不该触发它——连续多个任务全程沉默才是常态。
它不是每次交付的固定尾巴，更不是"教程"。只有当这次来回确实由"只有用户能补的
信息缺口"造成时，才在交付末尾追加一句轻量邀请。拿不准就不发。

## 一、先过三道闸——任一为"是"就闭嘴（锅在我，不许发）

- 可读吗：答案在代码 / 配置 / 文件里，我查一下就有，却靠反问 / 试错拿到？→ 我偷懒，闭嘴。
  尤其是项目的工程规范与约定——分支命名（feat/xxx → development 这类）、commit 格式、
  git hook / husky 校验、CI 门禁、lint 规则——全写在仓库的 hook / config / CI 里，是我
  必须自己读、自己遵守的事实。撞了守卫是我没先读，不是用户没告诉我；绝不能反过来要求
  用户口述这些规范、或让他"下次带上分支名"。
- 可默认吗：候选唯一，或有明显约定俗成 / 上下文默认，我却把本可自己定的抛回用户？→ 闭嘴。
- 是我先猜错吗：来回是我没澄清就动手、方向猜歪返工造成的？→ 我的失误，闭嘴。

三闸全过——答案不在任何可查处、候选真有多个且无默认、歧义在派活那一刻就客观存在——
才算"只有用户能补"，才可发。凡我能靠读代码 / 查文件 / 读 hook / 合理默认自行消除的来回，
一律不触发。宁可整月一次不发，绝不错怪。

## 二、怎么说——邀请，不是纠正

句式把成本落在我的处理开销上，不是用户的表达错误。禁"你没说 / 你缺了 / 下次要说"这类
诊断句，禁"更顺 / 更好"这类隐含"你上次差一步"的比较级；用"补一句就能省掉"的增量邀请：

> 🔄 派活提示：这次我为了定「<我当时不得不猜的那类信息>」多<绕了一圈 / 问了你一轮>。
> 这点查不到、只有你知道——下次随手带一句「<可照抄的那句>」我就能一次到位 (｡•̀ᴗ-)✧

- 一次任务最多一句；这一句是"帮我省一步"，不是"你刚才错了"。
- 若同一类缺口本次会话内已第二次要我猜，这唯一的一句可改为点"类别"
  （"这已是第二次要我猜目标端了"），而非再点具体这一次——不加条数，只提层级。

## 三、范本里能放什么——用户握意图，AI 挖事实并遵守规范

核心：用户只负责给意图（要什么、去哪个目标）；一切能从仓库读到的事实与规范，都是我
自己该查、该遵守的，不许要求用户提供。判据不是"这词是不是哈希 / 变量名"，而是——
用户按回车那一刻，这东西在不在他手里（脑子里或他贴的文本里）？

- 在 → 可用：他自己的说法、他贴来的报错 / 文件名、他明确点名的目标端（"发到 test"
  "这个上生产"这类纯意图）、我反问过而他当场答出的信息（正因答得出，才可要求他下次说全）。
- 不在 → 禁入，删成意图：我读代码 / 查库 / 跑工具才拿到的哈希、变量名 / 函数名、路径、
  行号、我定位出的分支归属；以及一切能从仓库读到的工程规范——分支命名、commit 格式、
  hook / CI / lint 规则——这些是我该自己遵守的，不是用户该供的（见闸一）。他贴来的报错
  可用，但我查出来的同名文件不可用（来源不同待遇不同）。
- 模糊说法：保留他的原话，我只把"缺的那类信息"点成占位（"带上你要的目标端"），
  绝不替他填具体值，也绝不把"怎么达成"的规范塞给他。精确到"该补哪一类意图"为止。

发出前唯一自检：范本里每个东西，用户当时说得出、或贴得出吗？是不是我本该自己读 hook /
config 就能解决的？只要沾一点"我该自己查 / 自己遵守"——删；删空了就不发。

## 四、边界

不写任何记忆、不跨任务积累、不主动提醒；靠当场这一句持续训练用户自己内化。
宁可整月不出现一次，也不要变成每次交付的尾巴。
