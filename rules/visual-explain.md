# 图示优先

解释"东西之间的关系"时，一段图胜过三段文字。凡是能画出来的，先画再补一两句说明；
不要用长段落描述本质上是空间结构的东西。

## 一、对话回复里用字符画

命中以下任一形态，先给图再给文字：

- **层级 / 目录 / 模块划分** → 树形图
- **调用链 / 数据流 / 请求生命周期** → 箭头链或泳道
- **状态流转 / 分支判断** → 状态图或决策树
- **方案对比 / 前后差异** → 左右并排两块，或 before/after 上下对照
- **时序（谁先谁后、谁等谁）** → 时间轴

规格：

- 纯 ASCII 字符（`+ - | > v ^ / \`）或轻量框线（`─ │ ├ └ ┌ ┐ ▼`），二选一别混用
- 宽度 ≤ 72 列，超了就拆成两张图；终端会折行的图等于没画
- 图里的文字尽量短标签（模块名、函数名），长解释放图外
- 不做装饰性 ASCII art（大标题、边框花纹、emoji 拼图），图只承载信息

示例形态（照抄结构，不照抄内容）：

```
请求进来
   │
   ├─ 命中缓存 ──> 直接返回
   │
   └─ 未命中
        │
        ▼
   core/api  ──>  后端  ──>  写缓存 ──> 返回
```

## 二、给人看的 md 文档里用 mermaid

**判据**：这份 md 是给人读的（README、设计文档、架构说明、交付报告、评审材料、
排查记录），就用 ```mermaid 画关键关系；只给 AI 读的文档（规则、skill、
AGENTS.md、领域知识库）不画——那些场景下图是噪音，纯文本更省 token 也更好匹配。

选型对照：

| 要表达的 | 图类型 |
|---|---|
| 模块/组件间依赖、数据流 | `flowchart` |
| 多方交互、请求响应顺序 | `sequenceDiagram` |
| 状态机、生命周期 | `stateDiagram-v2` |
| 数据表/实体关系 | `erDiagram` |
| 类型/继承结构 | `classDiagram` |
| 排期、阶段划分 | `gantt` |

约束：

- 一份文档里图不超过 5 张；每张图配一句"这张图在说什么"
- 节点标签用中文没问题，但含 `()` `:` `,` 等符号时必须加引号：`A["fetch(id)"]`
- 图只画主干路径，异常分支写在图下的文字里；把所有边都塞进一张图＝谁都看不懂

## 三、不要画的时候别画

- 一两句话说得清的线性事实（"改了 3 个文件"）——直接说
- 只有两个节点一条边的关系——一句话比图快
- 代码注释里不塞大图；确需图解的复杂算法，最多 5 行示意
- 已经有图能复用时不重画，指向原图即可
