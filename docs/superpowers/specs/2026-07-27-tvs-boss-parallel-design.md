# tvs-boss 重任务并行机制 —— 设计方案（临时稿，待定稿）

> 状态：**草案**。方向已定（内建并行，方案 A 波次并行为主干 + Workflow 补充条款），
> 细节可能随后续问题调整；定稿前不改任何 skill 文件。

## 一、背景：为什么要做

对比 OMC /team 后确认，tvs-boss 处理重任务"效果差、明显慢"的根因不在缺重型运行时，
而在三个结构性缺口（OMC 靠它们取胜，且全是 prompt 层面的便宜设计）：

1. **缺强制拆解阶段**——leader 收需求默认单 dev 扛全部，并行没机会发生；
2. **worker 无自流动**——每一棒（编码→审查→测试）都回 leader 排队，leader 回合数 = 棒数×需求数；
3. **lead 无持续驱动**——OMC 有 stop hook 代码级逼 lead 推进，tvs 靠 leader 自觉。

同时深挖确认了 OMC native 路径的机制含量很低（原子认领/状态机/max_fix_loops 均为
prompt 约定或死代码），而 tvs 的**回执必达**（Agent 返回值管道，harness 强制）与
**安全闸门**（分支/push/编排禁令机制化）反而是 OMC 没有的优势——优化必须保留。

## 二、决策

- **主干：方案 A 波次并行**（leader 驱动、按依赖分波、波内全并行）。
- **补充：Workflow 升级条款**（子任务多/依赖链复杂时，报备 boss 后用原生 Workflow 冲一波，
  取代现有"借 OMC /team"建议——Workflow 不绕分支/push 安全模型，/team 会绕）。
- **明确不做：方案 B 共享任务表自流动**（复刻 OMC）——放弃回执必达后需补 watchdog/
  心跳/重派一整套补丁，复杂度就是 OMC 踩过的坑。

## 三、机制设计

### 3.1 派活三查 → 四查（新增复杂度分级）

在 leader-protocol 第一节三查后追加：

```
④ 轻中重分级？ —— 重任务（判据见下）→ 走「重任务并行流水线」（新节）；
                   轻/中量 → 维持现有单线流水线不变。
```

重任务判据（满足任一）：
- 预估涉及 ≥3 个可独立验收的子交付（模块/文件簇）；
- boss 明说"整个模块/全部 XX/大重构"这类批量语义；
- 单 dev 预估要连续多轮才能扛完的体量。

### 3.2 重任务并行流水线（leader-protocol 新节）

```
需求（重）
   │  分支闸门照走：整个重任务跑在一条 boss 批准的功能分支上
   ▼
拆解阶段：并行派 tvs-explore（摸地形）+ tvs-planner（出子任务图）
   │  产出：子任务清单，每条含【范围=互斥文件簇】+【依赖】+【验收】
   ▼
波次执行：按依赖分波
   第1波（无依赖子任务）：一条消息并行 spawn N 个 dev ──全部回执到齐
   第2波（依赖已解）：同上 ──…
   │  编码阶段一律不 commit（共享工作区，靠范围互斥避冲突）
   ▼
汇合审查：一次审整体 diff（tvs-code-reviewer，附 diff 喂料）
   │  打回 → SendMessage 续派对应子任务的原 dev（无则新 spawn 降级）
   ▼
测试 → 按 §3.4 节奏 commit/push（子任务验收即 commit、闸口自动 push 功能分支）
     → 待提交（合干线），等 boss 拍板
```

关键规则：
- **范围互斥是并行的安全基石**：拆解产出的【范围】文件簇之间不得重叠；
  planner 发现天然重叠（如共享类型文件）→ 把重叠部分单拎成前置子任务（第 1 波先做）。
- **波内并行 spawn 必须在同一条消息里发出**（真并行，不是逐个等）。
- **每个子任务照常 TaskCreate/TaskUpdate**，boss 面板上看到的是子任务粒度的进度。
- **回执必达不变**：每个 dev 的回执仍是 Agent 返回值；波的推进条件 = 本波回执全部到齐。
- **失败处理**：某子任务回执"受阻/失败"→ leader 决定重派或降级为串行处理该子任务，
  不阻塞无依赖关系的其他波次成员。

### 3.3 Workflow 升级条款（替换第三节"重量级借 OMC /team"）

触发：子任务 ≥8 个，或依赖层级 >3，或波次模型明显浪费（波内耗时方差大）。
做法：leader 起飞前报 boss 一句，然后用原生 Workflow 的 `pipeline()` 按子任务图编排，
`agentType` 仍指向 `tvs-*` 角色定义（红线/回执随定义生效）。
安全：分支已在闸门钉死；Workflow 子 agent 无 push 能力；结果回 leader 账本。

### 3.4 提交/推送节奏（开发分支自动化，boss 反馈第 1 条）

现状两个极端都不对：一直堆本地（丢机器=丢活）/ 改一次 push 一次（噪音+慢）。
新节奏——**commit 跟验收走，push 跟阶段闸口走**：

```
commit 时机（功能/开发分支，自动，不请示）：
  - 一个子任务回执验收通过 → 立即 commit（一个子任务=一个 commit，天然原子）
  - 打回修复通过复审 → 追加 commit（或 fixup，按项目习惯）
push 时机（功能/开发分支，自动，不请示）：
  - 汇合审查通过后（代码已达"可给人看"水位）
  - 一条需求交付进入"待提交"时（等 boss 拍板期间远端已有备份）
  - leader 建议 boss /clear 重启前（保证上下文重启零丢失）
仍需 boss 拍板（不变）：
  - 合并进任何干线（test / dev / master）
  - 往干线分支直接 push
```

- 铁律措辞相应放宽："push 必须 boss 确认"收窄为"**干线** push / 合并必须 boss 确认；
  功能分支 push 按上述闸口自动"。
- 角色红线同步改：dev 的"绝不 push"改为"只允许 push 派工单指定的功能分支，
  且仅在 leader 指令下"（push 动作仍由 leader 在闸口统一触发，避免各 dev 乱推）。

### 3.5 微任务快通道（boss 反馈第 2 条：子 Agent 慢的根治）

**根因**：微任务（git 操作 / 改一行配置 / 跑一条命令）被 spawn 成完整队员后，
要付全套出生仪式——团队简报里"开工先吃记忆工程"（读 CLAUDE.md+rules+项目记忆+wiki）、
skill 触发检查、验证仪式——对 10 秒的正事这是 5 分钟的税。

双管齐下：

1. **leader 直接干（首选）**：给"leader 不动手"铁律开一个明确口子——
   **机械微操作**（git add/commit/push、改一行配置/环境变量、跑单条命令、重命名文件）
   leader 直接用 Bash/Edit 执行，不 spawn。判据：无需理解业务代码、一两个工具调用能完、
   结果可即时验证。超出判据（要读懂代码才能改）仍然派人。
2. **确需派人时走快通道**：派工单头部加标注块——
   ```
   【微任务】跳过记忆工程/wiki 预读，不探索代码库，直接执行下述步骤并验证。
   ```
   并配套：团队简报（CLAUDE.md 受管块）的"开工先吃记忆工程"条目加豁免句
   "派工单标注【微任务】时跳过本条"；角色选 cheap 档（haiku）承接。

### 3.6 worktree 位置固定（boss 反馈第 3 条）

需要 worktree 时（单项目多角色并行改同 repo、且文件簇无法互斥），位置**固定为
`<项目根>/.worktree/<分支名>/`**，不散落各处。配套：

- 申请话术固定："建议在 `<项目根>/.worktree/feat-xxx` 开 worktree（理由…），可以吗？"
- 项目 `.gitignore` 须含 `.worktree/`（leader 建 worktree 前检查，没有就顺手加上并 commit）。
- 用完清理：需求交付后 `git worktree remove`，不留尸体；`git worktree list` 出现
  `.worktree/` 以外的路径视为违规，leader 发现即纠正。
- 该约定同时写进角色红线（git-master 的 worktree 操作段）。

### 3.7 产出物规范（boss 反馈第 4 条：文档乱生不清理）

**根因**：回执模板只说"大产出落文件带路径"，没规定落点与生命周期——产物就近乱生
（`.tvs-boss/` 里、项目根上），且没有任何清理时机。

**落点：唯一工作目录。** 一切任务过程产物（审查报告 / 拆解子任务图 / 分析文档 /
问题清单）固定落：

```
<团队根>/.tvs-boss/work/<需求slug>/
```

- 派工单新增【产出目录】字段（leader 按需求 slug 填好），回执模板补一句
  "大产出一律写入派工单【产出目录】，落其他位置视为违规"。
- `.tvs-boss/` 顶层从此只允许：三件套（projects/rules/contracts）+ 面板启动器 + `work/`。
  leader 见到其他文件即视为违规产物，按下面生命周期处置。

**生命周期：需求交付即清。** 需求进入"完成"（Task 标完）时 leader 收尾三选一：

```
有长期价值、属于项目 → 移入项目 repo（docs/ 等），随功能分支 commit，进版本管理
是团队级慢变量       → 升华进 rules.md / contracts.md（三件套本来的职责）
其余（绝大多数）     → 整个 work/<slug>/ 目录删除
```

- 崩溃恢复 / 定期巡检时：`work/` 下没有对应在途需求（Task/git 均查无）的目录，直接清。
- 该规范与"记忆有界"铁律同源：`work/` 是显式声明的**运行态暂存区**，不是记忆；
  记忆仍只有三件套。

### 3.8 保持不变的部分

- 轻/中量任务：现有单线流水线原样保留（并行有拆解成本，小任务用不上）。
- 回执格式、角色定义生成（make-agents.mjs）、分支闸门、push 拍板、记忆有界：全部不动。
- 审查/测试仍是共享角色每单现起。

## 五、已拍板的调整（boss 反馈，2026-07-27）

1. **开发分支自动 commit/push**：commit 跟子任务验收走、push 跟阶段闸口走（§3.4）；
   干线 push/合并仍必须 boss 拍板。
2. **微任务快通道**：机械微操作 leader 直接干；确需派人则工单标注【微任务】豁免
   记忆工程预读 + cheap 档承接（§3.5）。慢的根因=不分量级的出生仪式税。
3. **worktree 位置固定**：一律 `<项目根>/.worktree/<分支名>/`，配 .gitignore 与清理纪律（§3.6）。
4. **产出物规范**：过程产物唯一落点 `.tvs-boss/work/<需求slug>/` + 需求交付即清
   （留存的进项目 repo 或升华进三件套）；`.tvs-boss/` 顶层白名单化（§3.7）。

## 六、待确定问题（open questions）

1. 重任务判据的阈值（≥3 个子交付）是否合适？
2. 汇合审查是"一次审整体 diff"还是"每波审一次"？（当前取前者，省审查出生税）
3. Workflow 条款的触发阈值（≥8 子任务）与 boss 报备格式。
4. 是否需要给"波间 leader 在场"加兜底（如 leader 变钝时的中断恢复措辞）。
5. §3.4 的 commit 粒度"一个子任务=一个 commit"是否符合各项目的 commit 习惯
   （有的项目可能要求更细/squash）。
