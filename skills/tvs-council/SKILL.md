# tvs-council：议会

议会围绕**一份草案**迭代：「书记」持有草案，四个视角席位对草案开 issue，「书记」逐条处置并出新版。分歧先由席位代裁，只有席位相左的才到发起人手上，且必须用白话写。未决 issue 归零是收敛信号，轮次上限由发起人开场时给出，拍板只由发起人说。

你是**主持人**：跑流程、取证、整理状态表、呈现、落盘。主持人不写草案、不开 issue、不处置 issue、不下结论。

主持人必须是主会话。子 Agent 或队员里不开议会：队员起不了命名子 Agent，席位回信也到不了它。

## 边界

- 议题假定已经说得清。目标、对象、边界三者缺二时提示先走 `tvs-deep-interview`，不开会。
- 不读、不写任何其他 skill 的记忆文件（`.memory/`、`.omc/`、auto-memory）。议会产物只落 `~/.tvs-council/`。
- 不做代码级根因诊断。议题需要读代码时，主持人只取事实，判断留给席位。

## 席位

| 席位 | 镜头（起点，不是边界） | 子 Agent 名 |
|---|---|---|
| 「思绪」 | 可能性：漏了哪条路、上限画到没 | `council-sixu` |
| 「架构师」 | 代价与卡点：付出什么、第一个卡在哪、证据够不够 | `council-jiagoushi` |
| 「穷查理」 | 死因：哪个前提错了整件事就塌、怎么便宜地验证 | `council-qiongchali` |
| 「用户」 | 对他人意味着什么：谁受益谁受伤、动机站不站得住、值不值 | `council-yonghu` |
| 「书记」 | 持有草案：起草、处置 issue、出新版、打包待裁决 | `council-shuji` |

席位名一律带「」。不带「」的"用户"指开会的真人，纪要与提示词里称为**发起人**。

四个视角席**每轮新建**，靠主持人下发的"本席状态表"记得自己说过什么；「书记」全场续接同一个子 Agent。席位提示词原文在 `references/seats.md`，投递时整段使用，不改写、不删减。

## 两个核心对象

**草案**：固定七节（目标与动机 / 方案 / 备选路与放弃理由 / 代价与卡点 / 前提与验证 / 影响面 / 未决项）。每节对应至少一个席位的镜头，任何席位都有可攻的节。

**issue**：席位对草案某一节的一条可证伪陈述，固定字段：针对、严重度（致命 / 需改 / 提问）、陈述、依据、定案方式。另有一种**替代路 issue**，针对整份草案而不是某一节。席位只产出 issue、反驳、表态、撤回 / 升级，不写文章。

issue 生命周期：

```
[open] --书记采纳--> [已采纳]（草案必须改，理由须写"改在 §几"和"不采纳会怎样"）
[open] --书记驳回--> [已驳回]（理由须可证伪）
[open] --书记标待验证--> [待验证] --主持人补证据--> 下一轮书记必须改判采纳或驳回
                                   --证据取不到--> [待裁决]
[open] --书记标待裁决 + 推荐--> [待裁决] --下一轮四席表态--> 无人反对 --> [暂定]（写入草案）
                                                          --> 有人反对 --> 进发起人清单（白话格式）
[暂定] --再下一轮无人反驳、发起人未推翻--> [已关闭]
[已驳回] --提出席位撤回--> [已关闭]
[已驳回] --提出席位升级--> 进发起人清单
发起人清单 --发起人裁决--> [已关闭]（裁决写进草案）
替代路 issue --书记只登记进 §2，不驳回--> 发起人决定是否展开
```

被驳回的 issue，提出席位下一轮只能二选一：撤回或升级。不能原话重提，不能换个说法重提。

## 流程

```
1  议题        发起人原话；发起人已给方案 ──> 直接作草案 v0
2  议题陈述    意图 / 约束 / 已知事实 / 发起人方案 / 轮次上限，发起人过目
3  摊事实      事实清单（本地现状 + 先人方案 + 外部权威），五席共用，编号连续
4  开路轮      无 v0：「思绪」∥「架构师」──> 「书记」起草 v1
               有 v0：「书记」把 v0 整理成七节 v1；缺节多时先补开路
5  质询轮      四席新建、并行：开 issue / 反驳 / 表态 / 撤回 / 升级
6  合并        「书记」处置全部 issue ──> 草案 vN+1 + 处置表 + 收敛状态
7  停下        主持人核对改动、呈现、补取证 ──> 等发起人
8  末轮        到上限或发起人喊"收尾"：只收表态、反驳、撤回、升级；「书记」打包
9  拍板        发起人逐条裁决，或回复概括行；"散会"则未拍板
10 落盘        ~/.tvs-council/<日期>-<议题>/
```

各步模板在 `references/protocol.md`。

### 1. 议题

发起人怎么说都行，不追问需求细节。发起人的话里已有具体做法（用什么、怎么做、分几步）就是草案 v0，原样保留。

### 2. 议题陈述

改写成五节：意图、约束、已知事实、发起人方案、轮次上限。删掉的只有对议会的要求（"别附和我"）和情绪句；发起人的倾向和方案**保留**，席位就是要对它开火。轮次上限发起人没说就问一句"最多陪跑几轮"；仍不给写"不设，由发起人喊收尾"。给发起人过目一眼，确认或修正后才开会。

### 3. 摊事实

主持人统一取证，整理成事实清单，五席共用，席位不各自取证。

| 事实类型 | 何时取 | 从哪取 |
|---|---|---|
| 本地现状 | 议题涉及已存在的东西（代码、文件、数据、配置、发起人过去的记录） | codegraph / git / 文件 |
| 先人方案 | 每场必取：议题所要做的事，网络上有没有成熟方案 | 联网搜索；每个方案记名称、来源、解决了什么、已知局限；搜不到写"未找到" |
| 外部权威 | 议题涉及可查证的外部事实 | 官方文档、论文、标准、公认共识；每条带来源 |

清单里每条编号，全场连续，后续轮次追加的证据接着编。清单只放事实，不放"这说明 / 所以"。三类都取不到时清单为空，仍然发给席位并明说。

### 4. 开路轮

用 Agent 工具起**命名**子 Agent（`subagent_type: general-purpose`，名字见席位表）。

- 无 v0：同一条消息里并行起「思绪」「架构师」，输入 = 该席提示词 + 议题陈述 + 事实清单 + 开路轮任务。收齐后起「书记」，任务是起草 v1。
- 有 v0：直接起「书记」，任务是把 v0 整理成七节 v1，内容不增不减，空的节写"发起人未提及"。v0 只覆盖 §1 一节时，先按"无 v0"补一轮开路再起草，否则首轮席位只能对空节开"提问"。

v1 全文呈现给发起人，写 `草案-v1.md`。不停下，直接进第 5 步。

### 5. 质询轮

每轮四席**新建**（Agent 工具，同名；旧实例不再使用），并行。材料落成一个文件，四席各自用 Read 读同一个文件，内容完全一致：

- 草案 vN 全文
- 上一轮处置表（首轮无）
- 未关闭 issue（待裁决 / 待验证 / 本轮新暂定）的陈述与依据原文
- 本轮追加的事实清单条目
- 发起人裁决与插话（有则附）
- 本席状态表（主持人整理，见 protocol.md；席位据此不重复自己说过的角度）

每席回信只含：新 issue（含替代路）、反驳、对待裁决项的表态、对本席被驳回 issue 的撤回或升级。四类都没有则回"本轮无 issue"。首轮至少一条从本席镜头开；第二轮起每席至少一条针对本席镜头以外的节。

席位调用失败按同名重起一次，仍失败则如实报告该席缺席，不由主持人代写。

### 6. 合并

四席回信收齐后落成文件，用 SendMessage 让「书记」读该文件。「书记」回信 = 草案 vN+1 全文 + 改动摘要 + 处置表（含反驳列）+ 待裁决清单（白话格式）+ 收敛状态。回信过长时分两条发。

### 7. 停下

主持人先做三件事：
- **核对**：处置表里每条"采纳"，在草案 vN+1 对应位置确认改了；没改的标"未核"退回「书记」补，不由主持人改。
- **补取证**：处置表里每条"待验证"，按定案方式取证，追加为事实清单新编号；取不到的记"未取到"，下一轮「书记」转待裁决。
- **落盘**：`草案-vN+1.md`、`issues-N.md`。

然后按 protocol.md 模板呈现：改动摘要、处置表、待你裁决（白话版）、暂定项、收敛状态。用 AskUserQuestion 停下：裁决 / 插话 / 再来一轮 / 拍板。发起人裁决原文写 `裁决记录.md`，作为下一轮材料。

发起人的裁决只发给「书记」写进草案，主持人不改草案。每轮停下不可豁免。发起人改题时回到第 2 步，草案版本号继续递增。

### 8. 末轮

到轮次上限，或无上限时发起人说"收尾 / 打包"，进入末轮：四席只收表态、反驳、撤回、升级，不接新 issue。「书记」出终版草案，把全部待裁决与暂定项按白话格式打包成一份清单，末尾加一行"以上未逐条回复的按推荐执行"。

### 9. 拍板

发起人逐条裁决，或直接回复概括行，即视为拍板；未逐条回复的按推荐写入，决策记录标"发起人概括拍板"。发起人说"散会"或不回复概括行：未裁项不进终版正文，只进 §6 标"待发起人"，结论写"未拍板，含 N 条未裁项"。

主持人不提议结束、不问"要不要收尾"。

### 10. 落盘

按 protocol.md 的纪要模板输出到对话并写入目录。纪要 = 最终草案全文 + 决策记录（每条 issue 的最终处置、理由、反驳、暂定 / 概括拍板状态）。发起人明确要求写进当前仓库时，只写纪要一份，路径由发起人指定。

## 主持人红线

| 禁止 | 识别 |
|---|---|
| 主持人自己扮演任何席位 | 同一上下文里出现草案正文、issue、处置理由由主持人写出 |
| 主持人处置或裁决 issue | 处置表之外出现主持人对某条 issue 的判断 |
| 主持人改草案 | 草案文件内容与「书记」回信不一致；核对发现未改只能退回「书记」 |
| 统计倾向 | 呈现语出现票数、多数/少数、"N 席认为" |
| 主持人回答"你觉得哪个好" | 回"我不投票"，把问题作为发起人插话进下一轮 |
| 发给四席的材料不一致 | 同一轮四席读的不是同一个材料文件；状态表以外的内容有差异 |
| 席位自行读仓库、读发起人记忆 | issue 依据引用了清单之外的本地材料 |
| 待裁决清单出现未解释的术语 | 发起人清单里有事实清单之外的名词而没有一句解释 |
| 未拍板就出纪要 | 发起人未说"拍板"、未回复概括行、未说"散会"就写了纪要.md |
| 未拍板的纪要里出现"建议采用" | 未拍板纪要的结论一节有"未拍板"以外的内容 |

## 常见偏差

- 议题陈述里删掉了发起人的方案或倾向。协议保留它们，席位对它开火才是议会的用处。
- 忘了问轮次上限。开场没问，末轮规则就无从触发。
- 席位回信写成了文章而不是 issue 列表。用 SendMessage 让该席按格式重发，不由主持人拆。
- 主持人在对话里粘贴材料全文。材料只落文件，席位用 Read 读，主持人上下文才不会先触顶。
- 被驳回的 issue 换个措辞又出现。主持人转发时不过滤，「书记」标"重提，视为撤回"。
- 「书记」把待裁决直接压给发起人。待裁决先经一轮四席表态，只有相左的才进发起人清单。
- 发起人清单里出现黑话。「书记」呈现前自检，术语首次出现须一句解释加一个例子。
- 「书记」采纳而草案未改。主持人核对后标"未核"退回，不代改。
- 待验证挂着不动。主持人每轮补取证是职责，取不到也要写"未取到"让「书记」转待裁决。
- 事实清单为空时不告知。要明说"事实清单为空"，席位才知道自己在无证据状态下开 issue。
