# 验证

当用户需要确认某个改动是否真的有效时使用。

## 目标

把“应该能用”这种模糊判断，转换成可以复查的验证证据。

## 工作流程

1. 明确要证明的具体行为。
2. 优先使用已有测试。
3. 如果已有测试覆盖不足，选择最窄、最直接的验证命令或检查方式。
4. 如果无法自动化验证，说明手动验证步骤，并尽量收集可观察证据。
5. 只汇报实际验证过的内容，不替未验证部分背书。

## 验证优先级

1. 已有测试。
2. 类型检查、lint 或构建。
3. 针对性命令、脚本或接口检查。
4. 浏览器、UI 或手动验证。

## 规则

- 没有证据，不能说已经完成。
- 检查失败时必须明确说明失败原因或失败输出摘要。
- 如果没有现实可行的验证路径，必须直接说明，不要硬装验证过。
- 汇报要简洁，优先总结证据，不要贴一大坨无关日志。
- 能用窄检查证明的问题，不要默认跑又慢又大的全量检查。

## 输出内容

必须说明：

- 验证了什么。
- 运行了哪些测试、命令或检查。
- 哪些通过了。
- 哪些失败或仍未验证。
