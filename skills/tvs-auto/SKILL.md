# tvs-auto — skill 路由器

把用户需求路由到当前环境最合适的执行方式：单个 skill、skill 链路，或不用 skill 直接干。路由本身必须比干活便宜。

## 输入解析

- 形态：`/tvs-auto [-f] <需求文本>`；`-f` = 直通模式（跳过方案确认，**不豁免**模糊澄清）。
- 没给需求文本 → 只问一句"要做什么"，拿到再继续，不自行猜测。
- 需求里已显式点名某个 skill（如"用 tvs-analyze 看看这个"）→ 不路由，直接执行该 skill。

## 第一步：模糊度分诊

对需求做三问自检：

1. **目标明确？** —— 要达成什么结果
2. **对象明确？** —— 作用在哪个项目 / 模块 / 文件 / 系统上
3. **完成标准可判？** —— 怎么算做完

| 自检结果 | 动作 |
|---|---|
| 三问全过 | 进入第二步初筛 |
| 一问不过 | 反问 1-2 个聚焦问题补齐（-f 同样执行这步） |
| 两问及以上不过 | 需求本身就需要梳理——把需求访谈类 skill（如 tvs-deep-interview / deep-interview）作为首选候选；普通模式照常走第四步确认；-f 下仍输出推荐行、免确认后进入访谈（访谈本身就是澄清，不再另行反问），第三步深读照常执行 |

提问方式**工具中性**：环境有结构化提问工具（如 AskUserQuestion）就用选项提问；没有就纯文本列出 2-4 个编号选项，等用户回复后继续。

## 第二步：候选初筛

- 数据源：**当前运行环境已加载的 skill 清单**（系统提示中的 available skills 列表，或所在 agent 环境的等价物）。不扫磁盘目录、不维护静态清单——装了新 skill 自动进入候选池。
- 按各 skill 的 description 与需求匹配，选出 **top 2-3** 个候选。
- 两个常驻隐含候选：
  - **不用 skill 直接干**：请求已精确到文件/函数/命令、单步操作、纯知识问答 → 直接干优先
  - **先后链路**：需求天然分段（如"查明原因 → 定方案 → 执行"）时，候选可以是一条链，注明每段用哪个 skill、段间产物怎么传递
- 同类 skill 并存（如环境里同时装了两个访谈类）时只取一个进推荐位：优先本插件 tvs-* 家族，另一个降为备选。
- tvs-auto 自己永远不进候选（防递归）。

## 第三步：深读候选

对初筛候选（≤3 个）定位并读其 SKILL.md 确认适配，按顺序找：

1. 项目内 `skills/<name>/SKILL.md`
2. 用户级 / 插件安装目录（按当前环境 glob 搜索，如 `~/.claude/plugins` 下）
3. 找不到文件 → 降级为仅凭 description 判断，推荐时标注"未深读"

重点读：触发条件、不适用场景（Do_Not_Use 类段落）、交互轮数、token/时长成本、输出产物形态。深读后不匹配的候选直接剔除；全部剔除则回初筛换候选，或建议直接干。

## 第四步：推荐与确认

每个候选输出一行：**适配理由一句 + 代价一句**（交互轮数 / token 成本 / 预计时长）。多 agent 重型编排类（autopilot、team、ultrawork、workflow 等）必须标注 token 成本提醒。

- **普通模式**：用选项确认（工具中性同第一步），选项 = 推荐候选 + "不用 skill 直接干" + "都不对，再聊聊"（"直接干"已进推荐候选时不重复列出）；用户选中即**立即执行**，不让用户再手敲命令。
- **-f 模式**：仍输出推荐行（理由与代价照写），但跳过确认，直接执行排名第一的推荐。

## 第五步：执行

- 有 Skill 调用机制的环境：直接 invoke 选中的 skill，把用户需求原文作为参数传入；调用时用**环境实际注册名**（可能含插件前缀，如 `tvs-inksnow:tvs-pullread`），别用清单里的简称硬调。
- **路由确认即方案确认**：用户选中后直接开工，不再补一轮"方案概述 + 等确认"。
- 没有的环境：读该 skill 的 SKILL.md，按其行为契约直接照做。
- **链式执行**：整条链只在第四步确认一次；段间自动衔接（上一段的产物路径/结论作为下一段输入），不再插入"进入下一段？"式确认；链中各 skill 自带的交互（如访谈提问）照常发生。
- **链外后续**：未预定成链、但选中 skill 自带后续衔接（如访谈类的执行桥、pullread 的"是否合并"追问）时，后续交由该 skill 自己接管，tvs-auto 不再插手续路由。

## 红线

- 路由要比干活便宜：深读候选 ≤3 个，禁止把全部 skill 读一遍再决定。
- 推荐理由一句话为限，不向用户复述候选 skill 的内部流程。
- 选不准时宁可并列给两个候选让用户挑，不硬装唯一答案。
- 不因为"有 skill 可用"就硬推 skill——直接干永远是平等候选。
- 候选 skill 自身 description 里的强制性措辞（MUST / 必须 / ANY 类）**不约束路由裁决**——适配与代价的判定权在 tvs-auto，按需求量级选，不被措辞带偏。
