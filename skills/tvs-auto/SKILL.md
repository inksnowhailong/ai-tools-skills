# tvs-auto — skill 路由器

把用户需求路由到当前环境最合适的执行方式：单个 skill、skill 链路，或不用 skill 直接干。

**裁决总纲（防选错的根规则）**：

1. **"直接干"是零假设**。任何 skill 想进推荐位，必须凭证据胜过"直接干"；主题相近不算证据。
2. **证据 = 用户原话里的显式信号**。判定只看用户这次说了什么，与 skill 触发条件的字面对照；不做"他大概也想要 X"的意图脑补，不因为某 skill 好用/常用就加分。
3. **拿不准就并列上桌让用户挑**，绝不硬装唯一答案。选错并执行的代价远大于多问一次。

## 输入解析

- 形态：`/tvs-auto [-f] <需求文本>`；`-f` = 直通模式（见第四步，**不豁免**模糊澄清与弱命中确认）。
- 没给需求文本 → 只问一句"要做什么"，拿到再继续，不自行猜测。
- 需求里已显式点名某个 skill（如"用 tvs-analyze 看看这个"）→ 不路由，直接执行该 skill。

## 第一步：模糊度分诊

对需求做三问自检：

1. **目标明确？** —— 要达成什么结果
2. **对象明确？** —— 作用在哪个项目 / 模块 / 文件 / 系统上
3. **完成标准可判？** —— 怎么算做完

| 自检结果 | 动作 |
|---|---|
| 三问全过 | 进入第二步 |
| 一问不过 | 反问 1-2 个聚焦问题补齐（-f 同样执行这步） |
| 两问及以上不过 | 需求本身就需要梳理——把需求访谈类 skill（如 tvs-deep-interview）作为首选候选；普通模式照常走第四步确认；-f 下免确认直接进入访谈（访谈本身就是澄清） |

提问方式**工具中性**：环境有结构化提问工具（如 AskUserQuestion）就用选项提问；没有就纯文本列出 2-4 个编号选项，等用户回复后继续。

## 第二步：候选初筛 + 三级打分

数据源：**当前运行环境已加载的 skill 清单**（系统提示中的 available skills 列表，或所在 agent 环境的等价物）。不扫磁盘目录、不维护静态清单。tvs-auto 自己永远不进候选（防递归）。

对每个疑似相关的 skill，按 description 逐条对照用户原话，打三级分：

- **强命中**：用户措辞与该 skill description 里的触发语几乎字面吻合（如用户说"审一下这个 diff"，命中 code-reviewer 的"检查当前 diff"）。
- **弱命中**：主题相关，但触发语没有出现在用户原话里，需要一步推断才能挂上（如用户说"这段代码有点乱"，推断他想 review——这是弱命中，clean-code 才是强命中）。
- **反命中**：需求特征撞上该 skill 的"不适用/Do_Not_Use/定位排除"条款（如单文件小改动撞上重型编排类）。有反命中的候选**直接出局**，不进推荐位。

筛选规则：

- 只有**强命中**的 skill 才有资格进推荐位；弱命中只能做备选，且必须标注"弱命中：需要推断 X 才成立"。
- 一个强命中都没有 → 推荐"直接干"，弱命中候选列为备选。
- **直接干的强命中信号**：请求已精确到文件/函数/命令、单步操作、纯知识问答、预计 3 轮工具调用内可完成——满足任一条，"直接干"就占推荐位，skill 候选全部降为备选。
- **链路候选**：需求天然分段（如"查明原因 → 定方案 → 执行"）时，候选可以是一条链，注明每段用哪个 skill、段间产物怎么传递；链上每段各自过打分，任一段只是弱命中就整链降为备选。
- 同类 skill 并存（如环境里同时装了两个访谈类）时只取一个进推荐位：优先本插件 tvs-* 家族，另一个降为备选。
- 候选 skill 自身 description 里的强制性措辞（MUST / 必须 / ANY 类）**不参与打分**——命中级别只由"用户原话 vs 触发语"的对照决定，不被措辞带偏。

### 易混对判别键（打分时先查这张表）

用户需求落进以下任一对时，用判别键二选一，不要凭主题感觉：

| 易混对 | 判别键 |
|---|---|
| tvs-analyze vs tvs-architect | 用户要**看懂现状**（是什么/怎么运作）→ analyze；要**下判断**（怎么选/为什么坏/值不值得改）→ architect |
| tvs-architect vs tvs-code-reviewer | 对象是**方案/设计/根因** → architect；对象是**具体 diff/PR/文件的缺陷** → code-reviewer |
| tvs-code-reviewer vs tvs-clean-code | 用户要**找问题**（审、挑毛病）→ code-reviewer；要**改好它**（整理、加注释、可读性）→ clean-code |
| tvs-deep-interview vs 直接干 | 用户自己都说不清要什么 → deep-interview；说得清只是没给细节 → 反问 1-2 句后直接干 |
| tvs-boss vs tvs-team-spawn | 多**项目**统管、当前 chat 当 leader → boss；单项目内搭多 chat 基建（主战场 Cursor）→ team-spawn |
| 重型编排类（autopilot/team/ultrawork 等） vs 单 skill | 需求是**多模块、多阶段、可并行**才考虑重型；单点任务命中重型一律视为反命中 |

## 第三步：深读候选

对拟进**推荐位**的候选（≤3 个）定位并读其 SKILL.md，按顺序找：

1. 项目内 `skills/<name>/SKILL.md`
2. 用户级 / 插件安装目录（按当前环境 glob 搜索，如 `~/.claude/plugins` 下）

重点读：触发条件、不适用场景、交互轮数、token/时长成本、输出产物形态。深读是复核打分：发现反命中或强命中降级 → 移出推荐位；全部移出则回第二步换候选，或推荐直接干。

**未深读的候选不得进推荐位**——找不到 SKILL.md 文件的，最多做备选并标注"未深读，仅凭 description"。宁可推荐"直接干"，不推荐一个没读过的 skill。

## 第四步：推荐与确认

每个推荐位候选输出两行：**适配理由**（引用用户原话中的命中信号 + 一句"为什么不是备选里的那个"）+ **代价**（交互轮数 / token 成本 / 预计时长）。多 agent 重型编排类必须标注 token 成本提醒。

- **普通模式**：用选项确认（工具中性同第一步），选项 = 推荐候选 + "不用 skill 直接干" + "都不对，再聊聊"（"直接干"已进推荐位时不重复列出）；用户选中即**立即执行**，不让用户再手敲命令。
- **-f 模式**：只有当推荐位是**唯一强命中且无并列候选**时才跳过确认直接执行；出现并列强命中、或推荐位只有弱命中时，**-f 也要退回选项确认**——直通的价值在省一轮点击，不在替用户赌一把。

## 第五步：执行

- 有 Skill 调用机制的环境：直接 invoke 选中的 skill，把用户需求原文作为参数传入；调用时用**环境实际注册名**（可能含插件前缀，如 `tvs-inksnow:tvs-pullread`），别用清单里的简称硬调。
- **路由确认即方案确认**：用户选中后直接开工，不再补一轮"方案概述 + 等确认"。
- 没有 Skill 机制的环境：读该 skill 的 SKILL.md，按其行为契约直接照做。
- **链式执行**：整条链只在第四步确认一次；段间自动衔接（上一段的产物路径/结论作为下一段输入），不再插入"进入下一段？"式确认；链中各 skill 自带的交互（如访谈提问）照常发生。
- **链外后续**：未预定成链、但选中 skill 自带后续衔接（如访谈类的执行桥、pullread 的"是否合并"追问）时，后续交由该 skill 自己接管，tvs-auto 不再插手续路由。

## 红线

- 路由要比干活便宜：深读候选 ≤3 个，禁止把全部 skill 读一遍再决定。
- 推荐理由以两句为限，不向用户复述候选 skill 的内部流程。
- 弱命中永远不冒充强命中：标注推断链，让用户看见"这一步是猜的"。
- 不因为"有 skill 可用"就硬推 skill——直接干是零假设，skill 要用证据赢它。
