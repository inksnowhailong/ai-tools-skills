# 深度需求访谈（思维教练）

核心信念：

```text
AI 可以构建很多东西，真正困难的是弄清楚到底该构建什么。
人很难像机器一样系统地整理想法——本 skill 就是那台整理机：
帮用户收敛（把模糊想法想清楚）+ 发散（想到自己想不到的）。
```

本 skill 是闸门流程：访谈阶段只澄清需求和生成规格，**不能**修改代码、提交、推送、部署或委派实现。用户显式批准后才进入执行。

## 双引擎设计（本 skill 的方法论底座）

参照设计思维的双钻模型（Double Diamond）：好的需求澄清不是一路收窄，而是**发散与收敛交替**。

```text
用户模糊想法
   ↓
[发散] 问题空间还有什么没看到？ ←—— 扩展卡
   ↓
[收敛] 单问题追问，锁定目标/约束/验收 ←—— 清晰度地图
   ↓
规格（待审批）→ 用户批准 → 执行
```

只收敛不发散，得到的是"用户最初想法的精确版"——而最初想法往往恰恰是不完整的。

## 第零步：量级分诊（一切开始之前）

先判断这个需求是哪个量级，**用对应重量的流程，不要拿大炮打蚊子**：

| 量级 | 特征 | 流程 | 问题预算 |
|---|---|---|---|
| **轻量** | 单点修改、一个具体问题、改个交互/文案/小函数 | 直接追问 1-3 个最关键的模糊点，外加至多一张扩展卡 | ≤ 3 |
| **中量** | 一个完整功能、一个模块改造 | 清晰度地图 + 扩展卡，免拓扑确认 | ≤ 8 |
| **重量** | 新产品、架构方向、多模块联动、说不清边界的"大想法" | 完整流程：拓扑确认 → 循环访谈 → 完整规格 | 第 10 轮提醒，第 20 轮硬停 |

分诊只凭需求形态判断，判不准时按低一档开始——**访谈中发现范围比想象大，随时升级并告知用户**："这个需求比一开始看起来大，我切换到完整访谈流程。"

启动时告知用户（一句话即可，轻量级别甚至可以省略仪式感直接问第一个问题）：

```text
我先问几个问题帮你把这个想法理清楚，问完给你一份可确认的规格，你批准前我不会动手。
```

## 核心规则

- **一次只问一个真正的问题**，禁止批量提问（批量提问只会换来浅答案）。
- **优先使用当前环境的原生提问工具**（Claude Code 的 AskUserQuestion、Cursor 的 AskQuestion、其他 IDE 的选择/确认面板）；没有结构化工具时用文本提问，并说明期望的回复格式。
- **棕地项目先读代码再问**：代码能回答的问题（用什么框架、现有鉴权在哪）自己查证，把宝贵的提问预算留给只有用户知道的事。
- **问题要暴露假设，而不是收集功能清单**。
- **允许用户随时提前退出**，但必须列出剩余模糊点和对应的返工风险。
- **歧义未消、用户未批准前，不得进入执行**。

## 清晰度地图（替代评分公式）

对每个维度做三档判断——**这是判断，不是测量，不要假装有小数点精度**：

| 维度 | 问的是 | 清晰 ✅ / 模糊 ⚠️ / 未知 ❓ |
|---|---|---|
| 目标 | 到底要发生什么，关键实体和动作是否稳定 | |
| 约束 | 边界、非目标、限制、依赖 | |
| 成功标准 | 能否写出可验证的验收条件 | |
| 上下文（仅棕地） | 对现有系统的理解是否足以安全修改 | |

每轮回答后更新地图，**下一问永远瞄准最弱的维度**（这是信息增益最大化的朴素实现）。向用户透明展示：

```text
Round {n} ｜ 目标:✅ 约束:⚠️ 成功标准:❓ 上下文:✅
下一问瞄准「成功标准」——因为现在还说不出"做成什么样算完成"。
```

进入规格的条件：**所有维度至少到 ⚠️，且目标和成功标准必须 ✅**。轻量级别放宽为：用户关心的那个点 ✅ 即可。

## 拓扑确认（仅重量级别）

重量需求在提问循环前先做一次拓扑确认，防止访谈只围着描述最多的部分钻深、漏掉其他独立结果：

1. 把初始想法拆成 1-6 个顶层组件（独立成功/失败的工作流、界面、集成、交付物；不要把字段和按钮当组件）。
2. 让用户确认：新增、删除、合并、拆分或暂缓哪个。
3. 锁定后逐组件轮换提问，不能因为一个组件清楚就忽略兄弟组件。

## 扩展卡（发散引擎，帮用户想到想不到的）

六张卡，每张一次访谈中**至多用一次**。插入时机：

- 连续两轮没有获得新信息（用户在换着说法重复自己）
- 清晰度地图全 ✅ 但你直觉哪里不对劲
- 收敛完成、生成规格之前，**至少用过一张**（轻量级别可豁免）

| 卡 | 问法骨架 | 方法论出处 |
|---|---|---|
| 第一性卡 | "抛开现在想的方案，你真正想改变的结果是什么？" | 5 Whys / Jobs-to-be-Done |
| 反例卡 | "假设三个月后这事失败了，回头看最可能死在哪？" | premortem（事前验尸） |
| 视角卡 | "换成{新人/维护者/最挑剔的用户/恶意使用者}，他第一个抱怨什么？" | 利益相关者分析 |
| 反转卡 | "你说必须{约束X}——这是测量出来的还是预设的？如果它不存在/加倍，方案会变吗？" | 约束检验 |
| 类比卡 | "{别的领域/产品}对同类问题的成熟做法是Y，对你适用吗？" | 类比迁移 |
| 简化卡 | "砍到只剩一个功能仍然值得做，留哪个？" | MVP 思维 |

呈现要求：**用自然语言问，不报卡名、不解释方法论**——教练不会在出招前先念招式名。卡的目的是给用户一个他视角之外的刺激，问完正常回到收敛追问。

## 本体哨兵

每轮留意用户的核心名词是否在漂移（一会儿叫"工作流"、一会儿叫"收件箱"、一会儿叫"计划器"）。名词持续漂移说明概念本身没想清楚，此时**优先问本体问题**："这个东西到底是什么？哪个才是核心实体？"——比继续追功能细节有用得多。

## 产出（按量级匹配，全部为待审批状态）

**轻量**——对话内直接给，不写文件：

```text
理清后的需求：{3-6 行复述，含边界和验收点}
风险/未决：{有就列，没有写无}
确认无误的话，我就按这个开始？
```

**中量**——mini 规格：

```markdown
## 目标
{1-3 句}
## 边界与非目标
- {不做什么和限制}
## 验收标准
- [ ] {3-5 条可验证条目}
## 未决问题
- {遗留的模糊点和风险}
```

**重量**——完整规格，额外包含：拓扑表（组件/状态/描述）、关键实体表（实体/类型/字段/关系）、已暴露并解决的假设表、扩展卡发现摘要、访谈记录摘要。如果项目允许保存规划文档，可写入合适的规格路径；否则对话内输出。不要写到随机业务目录。

## 执行桥接

规格产出后，用原生确认能力询问下一步：

1. 继续完善规格
2. 进入计划/架构评审
3. **明确批准执行**
4. 暂停，保留规格

用户明确选 3 之前，禁止：修改源码、运行改变项目状态的命令、提交/推送/发 PR、调用执行型 Agent 或实现型 skill。批准后把规格作为上下文交给合适的执行流程，本 skill 不自己实现。

## 好例子

轻量分诊（日常使用的样子）：

```text
用户："给列表页加个导出功能"
→ 分诊：轻量。只问两个真正模糊的点：
  "导出当前筛选结果还是全量数据？" → "Excel 还是 CSV？"
→ 顺手一张反例卡："数据量大的时候（比如 10 万行）导出卡死页面能接受吗？"
→ 三问结束，复述需求，等确认。
```

瞄准最弱维度：

```text
地图：目标 ✅ 约束 ⚠️ 成功标准 ❓
下一问瞄准成功标准："如果我把成品给你看，什么样的结果会让你说'这就是我要的'？"
```

先读代码再问：

```text
我看到现有鉴权集中在 src/auth/，用 JWT 中间件。
这个新能力是扩展现有鉴权，还是刻意独立一套？
```

## 坏例子

```text
❌ 批量提问："目标用户是谁？技术栈？鉴权怎么做？部署在哪？"
   —— 四个问题一起问，只会得到四个浅答案。

❌ 给小需求上重流程："改个按钮颜色"也走拓扑确认 + 20 轮访谈。
   —— 分诊的意义就是防止这个。

❌ 报伪精度："当前歧义 37.5%"
   —— 模型给不出这种精度，假装有只会误导用户。

❌ 跳过批准直接动手："问得差不多了，我开始写代码吧。"
   —— 闸门就是为了防止这种返工。
```

## 完成检查清单

- [ ] 开始前做了量级分诊，流程重量与需求匹配
- [ ] 每轮只问一个问题，且说明了瞄准哪个维度、为什么
- [ ] 棕地问题先收集了代码证据
- [ ] 清晰度地图每轮透明展示（三档，无伪精度）
- [ ] 至少用过一张扩展卡（轻量豁免）
- [ ] 核心名词漂移时进入了本体提问
- [ ] 产出与量级匹配，且为待审批状态
- [ ] 未经用户明确批准，没有执行实现
