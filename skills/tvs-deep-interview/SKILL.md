# 深度需求访谈

用于把模糊的产品或工程想法，整理成清晰、可验证、可执行的规格，再进入实现。

这个 Skill 不依赖特定工具、特定 IDE 或特定 Agent 体系。无论当前运行在 Cursor、Claude、VS Code、终端代理、网页对话，还是只能读取用户粘贴的文本，都应按同一套访谈方法工作，并优先使用当前环境自己的提问能力。

## 使用场景

当出现以下情况时使用：

- 用户只有一个大概想法，还没有明确需求。
- 用户明确说“先问我问题”“帮我澄清需求”“不要假设”“避免做错方向”。
- 任务复杂到如果直接写代码，很可能返工。
- 用户希望先得到规格、方案或执行范围，再批准实现。

不适用场景：

- 用户已经给出明确文件、明确行为、明确验收标准和明确实现意图。
- 只是一个很小的局部修改，直接执行比访谈更高效。

## 跨工具工作原则

- 如果当前工具能读取文件、搜索代码或查看项目结构，先用可用能力理解已有事实，不要让用户重复描述代码里已经写明的内容。
- 如果当前工具不能访问文件系统或项目上下文，明确说明限制，并请用户提供必要片段、目录结构、报错、截图或业务背景。
- 不要假设自己一定有终端、浏览器、MCP、IDE 或 Git 能力。
- 不要引用某个具体工具的专属命令作为前置条件；只有在当前环境明确可用时才使用。
- 输出结果必须能被其他工具或人工继续执行，不能绑定某个特定平台。

## 提问模块适配策略

访谈时要优先使用当前环境的原生提问/确认能力，而不是固定使用某一种工具。

适配优先级：

1. **当前环境提供结构化提问工具时，优先使用它。**
   - Cursor 中如果有 `AskQuestion` 这类结构化提问工具，优先用它收集单选、多选、确认类答案。
   - 如果其他 Agent/IDE 提供类似的选择、确认、表单或交互式提问工具，也优先使用对应工具。
2. **当前环境没有结构化提问工具，但支持普通对话时，用固定文本提问协议。**
   - 每次只问一个关键问题。
   - 必须使用下方“文本提问协议”的固定外框和字段。
   - 不要伪装成使用了不存在的工具。
3. **当前环境只支持命令行或非交互输入时，也使用固定文本提问协议。**
   - 明确告诉用户需要回复哪个字段。
   - 避免依赖弹窗、按钮、表单等能力。

常见环境参考：

- **Cursor**：优先使用 Cursor 提供的结构化提问工具，例如 `AskQuestion`；适合选择方案、确认范围、收集多选需求。
- **Claude / Claude Code**：如果当前会话提供原生交互、计划确认或问题收集能力，就使用其原生能力；否则使用普通文本单问题追问。
- **VS Code / 其他 IDE 插件**：如果插件暴露选择框、输入框或确认框工具，优先调用；没有则用聊天文本。
- **终端代理 / 网页对话**：通常用纯文本问题，必要时用编号选项。

原则：使用“当前工具实际存在的能力”，不要为了形式统一而强依赖某个生态。

## 文本提问协议

当当前环境没有原生结构化提问工具时，必须使用下面的固定格式提问。不要每次换一种问法。

外层使用 ASCII 框，标题固定为 `DEEP-INTERVIEW QUESTION`：

```text
╔══════════════════════════════════════════════╗
║ DEEP-INTERVIEW QUESTION                     ║
╠══════════════════════════════════════════════╣
║ 目的：说明为什么现在要问这个问题             ║
║ 类型：single | multiple | text | confirm     ║
║ 问题：这里写本轮唯一问题                     ║
║                                              ║
║ 选项：                                       ║
║ [A] 选项 A                                  ║
║ [B] 选项 B                                  ║
║ [C] 选项 C                                  ║
║ [OTHER] 其他，请补充                         ║
║                                              ║
║ 回复格式：A                                  ║
╚══════════════════════════════════════════════╝
```

字段规则：

- `目的`：一句话说明这个问题为什么影响需求判断。
- `类型`：
  - `single`：单选，只能选一个选项。
  - `multiple`：多选，可选多个，用逗号分隔。
  - `text`：开放题，用户直接写答案。
  - `confirm`：确认题，只允许 `YES`、`NO` 或 `ADJUST`。
- `问题`：本轮唯一问题，禁止一口气问多个问题。
- `选项`：只有 `single`、`multiple`、`confirm` 需要选项；`text` 可以省略选项。
- `回复格式`：必须明确告诉用户怎么回答。

选项规则：

- 选项编号固定使用 `[A]`、`[B]`、`[C]` 这种大写字母。
- 不使用 `1)`、`-`、`*` 作为选项标记，避免和普通列表混淆。
- 如允许用户自定义，最后一个选项固定为 `[OTHER] 其他，请补充`。
- 单选回复示例：`A`
- 多选回复示例：`A,C,OTHER: 还需要支持离线模式`
- 确认题回复示例：`YES`、`NO`、`ADJUST: 范围里去掉导出功能`
- 开放题回复示例：直接写自然语言答案。

开放题固定格式：

```text
╔══════════════════════════════════════════════╗
║ DEEP-INTERVIEW QUESTION                     ║
╠══════════════════════════════════════════════╣
║ 目的：说明为什么需要这段信息                 ║
║ 类型：text                                   ║
║ 问题：这里写本轮唯一开放问题                 ║
║                                              ║
║ 回复格式：直接描述你的答案                   ║
╚══════════════════════════════════════════════╝
```

确认规格时固定格式：

```text
╔══════════════════════════════════════════════╗
║ DEEP-INTERVIEW QUESTION                     ║
╠══════════════════════════════════════════════╣
║ 目的：确认是否进入实现，避免带着错误规格开工   ║
║ 类型：confirm                                ║
║ 问题：这个规格是否可以进入实现？              ║
║                                              ║
║ 选项：                                       ║
║ [YES] 可以，进入实现                         ║
║ [NO] 不可以，先暂停                          ║
║ [ADJUST] 需要调整，我会补充                   ║
║                                              ║
║ 回复格式：YES / NO / ADJUST: 你的调整说明     ║
╚══════════════════════════════════════════════╝
```

文本协议只在没有原生交互工具时使用。若当前环境有 `AskQuestion`、选择框、确认框或表单能力，应优先使用原生工具，而不是输出文本框。

## 核心规则

- 一次只问一个关键问题。
- 每个问题都瞄准当前最不清楚、最容易导致返工的点。
- 每次提问前，用一句话说明为什么这个问题重要。
- 优先提问能暴露假设、边界、验收标准和失败条件的问题。
- 不要在需求不清时急着实现。
- 只有当用户明确批准一个具体执行范围后，才进入实现。

## 清晰度维度

按 0 到 5 分评估，每轮访谈后更新最薄弱的维度：

- **目标清晰度**：完成后要产生什么结果？
- **用户/角色清晰度**：谁会在什么场景使用？
- **范围清晰度**：哪些在范围内，哪些明确不做？
- **约束清晰度**：技术、业务、数据、性能、安全、UX 上有什么限制？
- **验收标准**：如何判断它真的完成？
- **失败标准**：什么情况即使能跑也不能接受？
- **集成清晰度**：会影响哪些文件、系统、接口、数据流或工作流？

## 访谈流程

1. 用一小段话复述用户的初始想法，确认自己理解的方向。
2. 判断这是新功能、已有系统改造、bug 修复、重构、流程优化，还是混合任务。
3. 如果是已有项目，并且当前工具能读取代码，先查看最相关的代码路径。
4. 如果任务有多个部分，先问结构确认问题：

```text
我先把这个需求理解成几个部分：
1. ...
2. ...

这个拆分对吗？有没有需要新增、删除、合并、拆开或延后的部分？
```

5. 每轮只问一个最关键问题。
6. 用户回答后，更新清晰度判断，并继续追问最薄弱的部分。
7. 清晰度足够后，输出规格草案，并请用户确认、修改或暂缓。

## 常用问题类型

- 目标清晰度：完成后，用户能做什么以前做不到的事？
- 范围清晰度：第一版明确不处理哪些情况？
- 约束清晰度：有没有必须沿用的 API、数据模型、权限规则或 UI 模式？
- 验收标准：如果把结果展示给你，什么条件会让你判断“这就是我要的”？
- 失败标准：什么情况即使主流程能跑，也会让这个方案不可接受？
- 集成清晰度：它应该接入当前产品流程的哪个位置？

## 输出规格

当访谈足够清楚时，输出：

- 问题陈述。
- 已确认范围。
- 明确不做的范围。
- 用户流程或操作流程。
- 涉及的数据、API、UI、权限或系统变化。
- 验收标准。
- 验证计划。
- 仍未关闭的问题。

最后询问用户：

```text
请确认：这个规格是直接进入实现，还是需要继续修改范围？
```
