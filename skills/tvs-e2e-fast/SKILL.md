# tvs-e2e-fast — 端到端测试执行纪律

## 核心原则

**慢的根源是模型往返次数，不是浏览器。** 一切浏览器操作必须以"整段流程一次执行"为单位，禁止逐步操作。

## 执行阶梯（从上往下选，选中即停）

1. **项目里已有对应 spec** → 直接 `npx playwright test <文件>`，只读最终报告。
2. **流程会反复测**（≥2 次） → 先把流程写成 `.spec.ts` 存进项目 e2e 目录，再跑命令。写脚本的几秒远比逐步操作省。
3. **一次性临时验证** → 把"导航→登录→操作→断言"整条流程写成一段代码，塞进 **一次** `browser_run_code_unsafe` 调用执行完，只读返回结果。代码必须**分段标记**：每个阶段打 step 日志（`console.log('[step] 登录完成')`）或 try/catch 包段并在失败时返回步骤名——失败返回自带"死于第几步"，直接进失败分诊，不重跑、不逐步复现。
4. **执行失败** → 先走下方"失败分诊表"做一步定位；分诊全查不出，才允许 `browser_navigate` + `browser_snapshot` 逐步诊断，上限 5 步；5 步内没结论就停下向用户汇报现象，不许无限翻页。

**禁止**：默认用 browser_click/browser_snapshot 一步一步走完整流程。这是被封杀的旧模式。

## 失败分诊表（失败后的第一动作，每类只花一步）

按报错形态对号入座，先分诊再考虑逐步操作：

| 失败形态 | 一步诊断动作 |
|---|---|
| 连接拒绝 / net::ERR / 页面空白 | 被测服务没起——探测端口或 curl 首页；没起就先起服务（或问用户），别怪脚本 |
| 选择器超时 / 元素找不到 | 回项目源码 / 已有 spec 核对选择器写法，不去浏览器里翻页找 |
| 页面自身报错 / 行为异常 | `browser_console_messages` 一次拉完前端报错 |
| 操作成功但结果不对 / 疑似接口问题 | `browser_network_requests` 看请求状态码，锅在前端还是后端一眼分明 |
| 登录态相关（跳登录页 / 401） | storageState 过期——按下方规则重建一次，不逐步走登录 |

分诊出结论 → 修脚本重跑整段；全部查不出 → 才进阶梯 4 的逐步诊断。

## 依赖自动引导（进入阶梯 1/2 前执行）

- 阶梯 3/4 走 MCP 自带浏览器，**零依赖**，不检查不安装。
- 阶梯 1/2 需要项目内有 `@playwright/test`。执行前自检：`npx playwright --version` 失败或 package.json 无此依赖 → 自动安装，无需询问：
  ```bash
  npm i -D @playwright/test && npx playwright install chromium
  ```
  只装 chromium（够用且省磁盘），不装 firefox/webkit 除非用户点名要跨浏览器。
- 项目无 `playwright.config.ts` → 顺手生成最小配置：headless、`outputDir` 指向产物目录、`trace: 'retain-on-failure'`、有被测服务则配 `webServer`。

## 产物目录（截图/trace/报告统一归口）

所有测试产物一律存：`~/.claude/e2e-artifacts/<项目名>/`

- MCP 截图：`browser_take_screenshot` 必须传 filename 指向该目录，禁止落默认临时目录。
- spec 运行：`playwright.config` 的 `outputDir` 指向该目录（或运行时 `--output` 覆盖）。
- trace：只开 `--trace on-first-retry` 或 `retain-on-failure`，成功用例不留 trace。
- 用户随时可整目录删除，本目录内容永不作为长期依赖。

## 提速硬规则

- 登录态用 `storageState` 预热复用（admin/user 各存一份 json，存进产物目录），禁止每条测试走登录页。
  - **首次生成**：没有 state 文件时，用一段一次性脚本走完登录后 `context.storageState({ path })` 落盘——这本身也是整段执行，不逐步点登录页。
  - **过期处理**：加载 state 后首个页面若跳回登录页 / 返回 401，判定失效——自动重建**一次**再跑；重建仍失败才向用户要凭据或环境信息。
- 默认 headless；`webServer`（可数组）自动拉起被测服务，跨项目联测用多 `browser.newContext()` 在同一 spec 内完成。
- **每次验证必须有显式断言**：URL、页面文本、元素状态至少一项。"页面打开了没报错"不算通过，截图只是证据不是判据。
- 跑完只读汇总（pass/fail + 失败用例的错误信息），不逐条转述成功用例。

## 合理化借口对照表

| 借口 | 现实 |
|---|---|
| "先打开页面看一眼再决定怎么写" | 页面结构可从代码/已有 spec 推断；先写整段脚本，失败再看。 |
| "只是临时验证，不值得写代码" | 阶梯 3 就是为临时验证准备的，一次调用不比点一下贵。 |
| "选择器不确定，逐步试更稳" | 整段执行失败会返回具体报错，比逐步试错更快定位。 |
| "截图随手存一下而已" | 散落的截图=垃圾。必须进 e2e-artifacts 目录。 |

## 红线自检

出现以下念头立即停手，回到执行阶梯：
- 连续第 2 次调用 browser_click / browser_snapshot 而没有失败诊断的理由
- 失败后没查分诊表就想开始逐步翻页
- 准备宣布"验证通过"时拿不出一条显式断言
- 截图时没有指定 filename 路径
- 想"再多看几步就能明白"（已超 5 步上限）
