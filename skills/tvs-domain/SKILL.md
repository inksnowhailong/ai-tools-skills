# 领域知识引擎

记录项目的**业务领域知识**——不是代码结构（那是 codegraph/文档的事），是"资深工程师读完全部代码后仍然要问人的问题"。所有知识存在项目内 `domain/` 目录，markdown 格式，进 git。

**收录红线**：能从代码推导出来的（谁调谁、字段类型、接口签名、注释里已写明的取值含义）一律不收。收的是代码里读不出"为什么"和"业务上是什么意思"的东西。拿不准就问自己：新来的资深工程师读完代码后会问这个吗？会问才收。

**锚点信息差测试（写入任何条目前必须执行）**：条目内容在锚点处（注释/类型/命名）是否已明文可读？是 → 拒收——那是代码注释的职责，抄进来只会制造第二份会过期的真相。条目的价值 = 条目内容与锚点内容之间的信息差。

## 存储结构

```
domain/
  OVERVIEW.md      # 总览索引（百行内），挂进项目 CLAUDE.md 常驻
  订单.md           # 领域文件，按业务领域切分
  结算.md
  ...
```

### OVERVIEW.md（只做索引，不存分数、不存知识正文）

```markdown
# 领域总览
> 使用协议（对 AI）：写业务代码前，任务命中下方清单的关键词/目录 → 读对应领域文件。
> 条目分数行为：1分=推断（阻断型先问再写；数值类照写+插 TODO(业务待确认) 注释）；
> 2分=可直接用；3~4分=放心用；5分=冲突时以它为准；带 [待复核] 标记的按 2 分对待。
> 更新/纠正/新增领域知识时，调用 tvs-domain skill 按写入协议执行（升分、墓碑、冲突仲裁）。
## 系统定位
{一句话：这个系统是干嘛的、服务谁}
## 上下游地图
{对接哪些外部系统，各自一句话}
## 全局术语索引
| 术语 | 所在文件 |
## 领域文件清单
- 订单.md — 关键词：关单/退款/超时/预售 | 目录：src/order/**
```

领域文件清单每行带**业务关键词 + 顶层目录 glob**（只写到顶层目录粒度，如 `src/order/**`，避免重构后索引腐烂；不写具体符号名）。

### 领域文件与条目格式

条目是**打分、检索、引用的原子单位**。每个条目有永不复用的稳定 ID：`{域前缀-序号}`，如 `{#ORD-007}`。**改标题不改 ID，删条目 ID 作废不回收。** 墓碑、OVERVIEW 索引、跨文件指针一律引用 ID 而非标题。

```markdown
---
domain: 订单
prefix: ORD
nextId: 8
---
# 订单域

## 术语
### 预售单 {#ORD-001} [3分 | 对话 | 2026-07-08 | src/order/presale.ts]
定义：……
不是什么：不是"预占单"（t_order.type=3），预售单不占实时库存

## 规则
### 关单必须同步释放库存 {#ORD-007} [2分 | 代码互证 | 2026-07-08 | src/order/cancel.ts]
规则：任何路径的关单（超时/人工/风控）都必须发库存释放事件——库存服务不感知订单状态，这个契约分散在三条关单路径里，单看任何一处都以为只是本地状态变更（超时窗口时长读 config.order.payTimeout，可读值不抄进条目）
错误写法：cancel 里直接改 status 不发库存释放事件 → 库存永久占用

## 流程
### 下单到发货 {#ORD-003} [2分 | 代码互证 | 2026-07-08 | src/order/flow/]
{业务层面的步骤、触发者、分支条件——不是函数调用链}

## 对接
### 库存系统 {#ORD-005} [1分 | init扫描 | 2026-07-08 | src/client/stock.ts]
{对方是什么系统、交换的数据业务上代表什么、哪边是权威数据源}
相关域：→ 见 库存.md {#STK-002}

## 墓碑
- 2026-07-08 {#ORD-007}：曾推断「关单窗口 15 分钟」，用户纠正为 30 分钟
```

条目元数据四元组：`[分数 | 来源 | 确认日期 | 代码锚点]`。代码锚点是该知识对应的代码位置（文件/配置项），用于定位改哪里 + 过时检测；锚点本身不算违反收录红线——收的是不可推导的业务含义，锚点只是把它钉到代码坐标上。

**字段要求**：
- 术语的"不是什么"必须指向代码中**真实存在**的易混对象（另一个字段/状态/表），指不出来就不写这个字段。
- 规则不写"为什么"散文，写"**错误写法**"：错误代码长什么样 + 业务后果。生成代码时逐字对照的是反例。
- 跨域知识：本体只写在主责域文件（单一事实源），相邻域文件放一行指针 `→ 见 xx.md {#ID}`。

## 可信度分数（1~5）

分数管的不是"能不能用"，是**"用之前要不要问、问得多急"**：

| 分 | 含义 | 使用时行为 |
|---|---|---|
| 1 | AI 扫描推断 | 见下方两档处理 |
| 2 | 跨多处代码拼合才可见的隐性契约（单点锚点读不出全貌） | 可直接支撑写代码，顺手可确认 |
| 3 | 用户顺带提及印证 | 放心用 |
| 4 | 用户被直接问过、明确回答 | 放心用 |
| 5 | 用户主动书写/纠正 | 与其他知识冲突时以它为准 |

**1 分知识按影响分两档**：
- **阻断型**（写反会产生相反业务逻辑：权威数据源方向、状态流转顺序、资金/库存增减方向）：先问用户确认，再写代码。
- **标注型**（数值、文案、时间窗口类）：照当前值写，但在代码相应位置插 `// TODO(业务待确认): xxx 为推断值`，并在本轮交付摘要里集中列出待确认清单。

**过时检测（事件驱动，不做时间衰减）**：用户确认过的分数（3~5）**永久有效，不随时间降级**——业务规则不按日历过期。过时的唯一信号是代码锚点变更：增量重扫发现某条目的锚点文件在此期间有 commit 变更 → 该条目加 `[待复核]` 标记；带 `[待复核]` 的条目引用时按 2 分对待，向用户确认后去掉标记并刷新日期。

## 升分与写入协议

**升分只靠用户信号，纯粹被使用不升分**（沉默不是证据，防止系统把自己的幻觉刷成高可信）：
- 用户顺带提及印证 → 3 分
- 用户被直接问、明确回答 → 4 分
- 用户主动书写/纠正 → 5 分

**写入流程（对话中触发领域知识更新时）**：
1. 先按 ID 前缀/术语/关键词在目标域文件内搜索，命中已有条目 → 更新原条目（分数取高、日期刷新），不新增。
2. 拟落 3 分及以上的新知识，必须**当轮复述确认**：把即将写入的条目原文贴给用户（"我准备记录：xxx，对吗？"），用户点头才落 3/4 分；没确认只能落 1 分并加 `[未确认]` 标记。
3. 发现语义矛盾且双方分数 ≥3：**不覆盖、不并列**，合成一条 `[冲突待仲裁]` 条目（含双方内容、来源、日期）。之后任何时候引用冲突条目，必须先向当前用户求证，求证结果落 5 分并关闭冲突。
4. 用户明确否定/修正：立即生效改条目（新内容按用户信号定分），同时在墓碑区落记录：`日期 {#ID}：曾推断「X」，用户纠正为「Y」`。墓碑是系统里唯一不许被遗忘的东西。

## 读取协议（编写业务代码前）

1. 任务涉及的文件路径/业务关键词命中 OVERVIEW 清单里某域 → 读该领域文件。
2. 领域文件超过 150 行时不读全文：按 ID/业务关键词 grep，读命中条目及上下 10 行。分数在条目标题行，随任意片段可见。
3. 条目里有 `→ 见 xx.md {#ID}` 指针 → 跟过去读被指条目（跨域规则藏在这，漏读是最致命的静默失败）。
4. 按分数行为表执行（1 分两档、鲜度降级）。

## init 流程（一次性建库）

用户明确要求时执行：
1. 扫描项目：README、配置、入口、核心业务模块、对外接口。扫描目标**不是"总结业务术语/规则"**（那只会抄出代码注释，全军覆没于红线），而是**找缺口和矛盾**：无注释的魔数、语义疑似重叠的字段对、无维护说明的硬编码表、两处代码互相矛盾处、注释里引用外部决定/文档的地方。系统定位、领域划分、上下游地图（OVERVIEW 部分）照常提炼。
   > 委托规则：若把扫描派给子 agent，提示词必须原文携带收录红线与锚点信息差测试，且要求返回"读完代码后仍要问人的问题/发现的矛盾"，禁止要求其"总结业务术语/规则/流程"。
2. init 的主产出是**按域分组的阻断型问题清单**，逐批问用户（不限 3~5 个，问完为止），答案落 4 分——库的出生主体就是这些 4 分条目，不是扫描推断。
3. 生成 OVERVIEW.md + 按领域切分的领域文件。1 分条目只准收两类：(a) 扫描发现的矛盾/歧义观察本身（"字段 X 与 Y 疑似重叠，边界不明"）；(b) 跨多处代码拼合才可见的隐性契约（此类可标 2 分）。凡通不过锚点信息差测试的一律不写。
4. **把触发挂进常驻上下文（这步不做，场景②的自动触发就是空话）**：直接向项目 CLAUDE.md（或 .claude/CLAUDE.md）追加以下三行；用户不同意写入时才降级为口头提示：

   ```markdown
   ## 领域知识库
   本项目有业务领域知识库 `domain/`（@domain/OVERVIEW.md）。
   写业务代码前按 OVERVIEW 使用协议读取对应领域文件；对话中确认/纠正业务知识时调用 tvs-domain skill 更新。
   ```

**增量重扫**（用户要求"重新扫描"时）：重扫结论与存量条目按 ID/术语匹配——
- 一致 → 刷新代码锚点与日期
- 矛盾且存量 ≥3 分 → 存量不动，条目加 `[代码与知识不一致]` 标记（代码错了或业务变了，都值得问人）
- 矛盾且存量 ≤2 分 → 直接覆盖
- 撞墓碑 → 维持墓碑结论，跳过重推断
