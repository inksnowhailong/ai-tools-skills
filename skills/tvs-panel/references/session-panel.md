# 会话面板：形态由这场工作的形状决定

这是 `tvs-panel` 的默认模式。用户敲这个 skill，是因为**对话装不下他要的东西**：对话是一条时间线，只有先后没有并列；而他脑子里那件事是有结构的——几条并行的线、几个悬着的决策、一张关系网。时间线把它拍扁了，往上一顶就再也看不见全貌。

面板补的就是这一维：**对话继续做事件流，面板呈现当前状态**。

不要做成任务清单。任务清单是 `tvs-task` 的事，这里要做的是**这场工作此刻的样子**。

## 第零步：先判断该不该建

**这件事的结构一句话说得清，就别建。** 建一块面板要设计页面、开一个共享库、之后每有进展还得写库；换来的如果只是把三行字挪到网页上，那是净亏——烧了 token，还多一个会过期的东西要维护。

不建的情形：

- 一两步能做完，或全程不会出现第二个悬着的问题。
- 结构是线性的（照着清单往下做），用户扫一眼对话就知道到哪了。
- 用户要的是答案不是过程（"这个报错什么意思"）。

**建的情形是这三条同时成立**：会跨多轮、同时有两条以上并行的线或悬着的决策、用户需要反复回看全局。拿不准就先不建，等真出现第二个决策点再建——那时它的价值才是明确的。

用户直接点名要面板时照建，不要反过来劝他；但一件小事被要求建面板，就做最轻的一版，别按下面的完整形态铺开。

## 第一步：问形状，不是问类型

不要去想"用户在做的是什么类型的任务"——按类型对照模板，遇到没列过的类型就只能硬套。改成问一句：

> **这场工作里，他最需要一眼看到的「关系」是什么？**

从答案反推形态：

| 他要看的关系 | 形态 | 必备元素 |
|---|---|---|
| 哪个原因站得住 | 假设与证据 | 候选假设、各自的支持/反证、已排除的、当前最可能的 |
| 东西怎么连 | 节点与边 | 组件、依赖方向、数据流、边界 |
| 动了哪儿、还没动哪儿 | 触及面与覆盖 | 涉及的文件/模块、已改/待改/有风险、覆盖度 |
| 走哪条路 | 分支与取舍 | 决策点、各选项及代价、选了哪条、封存哪条（封存的要留着，他会回头问） |
| 到哪一步了 | 序列与位置 | 阶段、当前位置、卡在哪、下一步 |
| 选哪个 | 候选与维度 | 候选 × 评价维度矩阵、各格证据、当前倾向 |
| 数在怎么变 | 量与趋势 | 指标、时间轴、基线、异常点 |

**这张表是起点不是边界。** 真实工作常是两三种叠着的——排查 bug 排到一半发现要改架构，形态就从"假设与证据"长出一块"节点与边"。该叠就叠，不要硬塞进一种。

表里没有的关系，按同样的方法自己长：先说清"他要看的是什么关系"，再决定用什么画它。

## 第二步：固定骨架，三段不可省

不管形状是什么，这三段必须在，且按这个顺序：

```
现在在做什么     一句话。不是"正在分析"这种废话，是"正在验第 3 个假设：连接池耗尽"
等你定的         ← 这段永远在
已经确定的       已经拍过板、验过的事实。防止绕回去重新讨论
```

**「等你定的」是这块面板存在的首要理由。** 用户的原话是"出现三四个决策点，每处理一个页面都往上顶，把控不了多分支路途"。所以：

- 没有待定项时也留着这段，写"暂无"——它的位置要稳定，他扫一眼就知道有没有事等他。
- 每条待定项写成他能直接回答的样子：**问题一句 + 选项各自的代价 + 你的推荐**。不要只抛问题不给判断。
- 他定完的条目移进"已经确定的"，不要删——删了他回头会找不到当时为什么这么定。

## 第三步：怎么建、怎么更新

页面**当场为这场对话设计**，不套预制模板；内容走共享数据库，页面只是渲染器。

```
建一次页面（HTML 定制这场工作的形态）
      ↓
后续只写 db（ArtifactData），页面订阅自动刷新
```

这样定制和省钱兼得：**形态是定制的，更新是增量的**。别每次改动都重发整页 HTML——那会把 token 烧在重复的样式和结构上。

- 声明 `capabilities: {"db": {}}`，页面用 `claude.use("db")` 订阅。
- 集合名自己定，贴合这场工作（`hypotheses` / `modules` / `touched` / `decisions`…）。
- 形状中途长出新的一块，就加一个集合 + 页面加一区重发一次，不推翻重来。

**更新时机**：有新发现、待定项增减、状态变化时当轮写。不要攒——攒到最后就退化成了会议纪要，而他要的是"随时瞥一眼就知道现在什么情况"。

### 新鲜度：必须真做出来，不是提一句

**过期的面板比没有面板更糟**——它会让他以为自己看到了真相。所以每块面板都要能自己说出"这上面的东西是什么时候的"。三件事缺一不可：

1. **每条文档写入时带 `syncedAt: new Date().toISOString()`。**
2. **页面取所有文档里最旧的那个**（不是最新的——最新的会把没更新的那半边也说成是新的），换算成"N 分钟前同步"显示在标题旁。
3. **超过 30 分钟转警示色**，并且页面自己 `setInterval` 每分钟重算一次相对时间——否则页面开着不动，那行字就永远停在"刚刚同步"。

```js
// 页面里的最小实现
function oldest(list) {
  var t = null;
  list.forEach(function (d) {
    var v = d.syncedAt && new Date(d.syncedAt).getTime();
    if (v && (t === null || v < t)) t = v;
  });
  return t;
}
setInterval(renderFreshness, 60000);
```

### 字段契约

页面指望的字段由你自己定，但**定了就要防漂移**：后面改了写库的字段名而忘了改页面，页面会静默少渲染一整块，看不出任何异常。最省事的做法是页面检查一遍——某个关键字段在该集合**所有**文档里都不存在，就在区标题旁显示一行警告，而不是默默不画。

## 边界

- **面板不替代对话。** 他的决定仍然在对话里给，面板只是让他看清了再决定。不要在面板上做需要他点击回答的交互（那会把决定分散到两个地方）。
- **不写他没让你记的东西。** 面板是这场工作的投影，不是日志，更不是记忆。
- **会话结束面板就没用了**，不必留存、不必归档。要长期跟踪的东西属于 `tvs-task`，不属于这里。

## 收摊

会话面板是一次性的，但它**不会自己消失**——每建一块就在用户的 artifact 列表里留一条。不管，一个月后那里全是同名的废板。

所以这场工作收尾时（用户说"做完了/可以了/换个事"，或最后一个待定项定完），**主动问一句**："这块面板还留着吗？不留我删掉。" 用户说删就用 Artifact 工具 `delete`，说留就留着不再提。

只问一次，得到答复就照办；用户没回应不要追问，也不要替他删——**删是不可逆的**。

## 与标准模式的关系

`tvs-task` / `tvs-council` / `tvs-boss` 调用本 skill 时**不走这套提示词**——它们有各自的固定页面形式（见 SKILL.md）。本文只管默认模式：用户直接敲 skill、为当前这场对话建面板的情况。
